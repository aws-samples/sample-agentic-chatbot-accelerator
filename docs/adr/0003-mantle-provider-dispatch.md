# 0003 — Provider→builder dispatch for Bedrock Mantle models

- Status: Accepted
- Date: 2026-07-27

## Context

`BaseAgentFactory.create_model` (`src/agent-core/shared/base_factory.py`) is the single point where every agent pattern (single, agents-as-tools, swarm; graph inherits via A2A) constructs its LLM. Today it always returns a `strands.models.BedrockModel` (the Bedrock **Converse** path). Converse only covers models AWS has given a Converse integration; the fast-moving open-source model tail (Gemma, Qwen, DeepSeek, GLM, Kimi, …) lands on the newer **`bedrock-mantle`** endpoint first — sometimes Mantle-only — and is therefore unreachable from the accelerator.

Three facts shape the decision (verified against `strands-agents==1.41.0` and AWS docs on 2026-07-27):

1. **`bedrock-mantle` is multi-protocol, not OpenAI-only.** It exposes Chat Completions + Responses (OpenAI-compatible) **and** the Anthropic Messages API ([endpoints.html](https://docs.aws.amazon.com/bedrock/latest/userguide/endpoints.html)). Each model speaks the protocol native to its provider: the OSS tail + OpenAI → Chat Completions; the newest Claude → Messages; Nova is absent from Mantle entirely.
2. **The Mantle model set changes on every AWS release.** A hardcoded allowlist goes stale immediately (Gemma 4, GPT-5.6 variants already present). The endpoint publishes its own catalog via the OpenAI-standard `GET /v1/models`.
3. **Strands support is asymmetric.** `OpenAIModel` has a turnkey `bedrock_mantle_config`; `AnthropicModel` has no Mantle helper — it takes `client_args` passed straight to `anthropic.AsyncAnthropic(**client_args)`.

## Decision

1. **`create_model` becomes a provider→builder dispatch**, not a binary "use Mantle" flag:
    - model on Mantle, `anthropic.*` → `AnthropicModel(client_args={base_url: "…/anthropic", api_key: <minted token>}, …)` (Messages).
    - model on Mantle, `openai.gpt-5.*` → `OpenAIResponsesModel(model_id, params=…, bedrock_mantle_config={"region": AWS_REGION})` (**Responses API** on the OpenAI-proprietary passthrough `…/openai/v1`).
    - model on Mantle, anything else (OSS tail incl. `openai.gpt-oss-*`) → `OpenAIModel(model_id, params=…, bedrock_mantle_config={"region": AWS_REGION})` (Chat Completions, `…/v1`).
    - model not on Mantle (Nova, older Claude/OSS-via-Converse) → `BedrockModel(**model_args)` — **exact current behavior, unchanged**.

    > **Amendment (2026-07-27, after live validation).** The original decision assumed a 3-way split with a single OpenAI-compatible surface (Chat Completions). Live testing against `bedrock-mantle.us-east-1.api.aws` and the AWS model cards proved a **fourth** branch: the OpenAI proprietary line (`openai.gpt-5.*` — 5.4/5.5/5.6) is served **only** via the **Responses API** on a distinct `…/openai/v1` path and rejects Chat Completions (`400: does not support '/v1/chat/completions'`). The OSS tail — including OpenAI's open-weights `openai.gpt-oss-*` — stays on Chat Completions at `…/v1`. This is a **documented AWS provider convention** ("this `openai/v1` path is specific to the OpenAI models"), not a per-model quirk: strands 1.50.1 encodes it in `_openai_bedrock._OPENAI_PATH_MODEL_PREFIXES = ("openai.gpt-5.",)` and resolves the base path automatically inside `bedrock_mantle_config`. `create_model` mirrors that one prefix only to select the matching Strands _class_ (`OpenAIResponsesModel` vs `OpenAIModel`), since the config picks the path but not the API surface.
    >
    > **Second amendment (2026-07-28, T6 live validation).** The `/v1` vs `/openai/v1` split is **not** limited to `openai.gpt-5.*`. A full catalog sweep + the AWS model cards showed `google.gemma-4-*` and `xai.grok-4.*` do **Chat Completions**, but only on the `/openai/v1` passthrough — `/v1` returns `400: "model isn't supported on this route"`. Strands' `bedrock_mantle_config` cannot target `/openai/v1` for a Chat Completions model (its `_OPENAI_PATH_MODEL_PREFIXES` only covers `openai.gpt-5.*` and it always picks the Responses class for that path), so `create_model._build_openai_mantle` routes `_MANTLE_OPENAI_V1_CHAT_PREFIXES = ("google.gemma-4", "xai.grok-4.")` by building `client_args` (`base_url` = `…/openai/v1` + minted token) itself — the same technique as the Anthropic branch. This set is a **maintained prefix list**, an accepted exception to the "no static list" principle in Decision 2: the serving path is model metadata the catalog does not expose (`/openai/v1/models` 404s; `/v1/models` lists all models regardless of path), so there is no dynamic signal to route on. It never affects Mantle _membership_ (still fully dynamic) — only the base path for models already known to be on Mantle. See [Bedrock Mantle Models](../src/mantle-models.md) for the full working set.

2. **Mantle membership is discovered dynamically** from `GET /v1/models`, fetched once at container/module load and cached process-local (success only). New OSS models route correctly with no code change. On fetch failure the catalog is treated as **empty** — no model matches, so routing degrades cleanly to Converse — and the failure is not cached (next call retries). There is **no static allowlist fallback**: a hardcoded seed set would be arbitrary, incomplete, and stale-prone, reintroducing exactly the anti-pattern this dynamic discovery exists to avoid.

    > **Note on the `openai.gpt-5.` prefix vs. the "no allowlist" principle.** The `/v1/models` catalog lists GPT-5.x and the OSS tail identically and there is **no** `/openai/v1/models` catalog (it 404s), so _membership_ is still fully dynamic (the prefix is never used to decide whether a model is on Mantle). The prefix decides only _which API surface_ a known-on-Mantle OpenAI model speaks — a stable provider convention, maintained by strands, analogous to the existing `anthropic.` prefix check. It is not a per-model membership list and does not go stale as AWS adds OSS models.

3. **Build the Anthropic-Messages-via-Mantle branch now**, despite the lack of a strands helper, by injecting `base_url` + minted bearer token into `client_args`. Both Mantle branches share one token/region helper (`aws_bedrock_token_generator.provide_token`).

## Consequences

- **Positive:** The OSS long tail becomes reachable the moment AWS lists a model on Mantle — the core goal — without per-model code edits.
- **Positive:** Non-Mantle models (Nova, older Claude) keep their proven Converse path, including prompt caching and reasoning wiring; zero regression risk for the default catalog.
- **Positive:** One shared token/region helper keeps the two Mantle branches consistent and testable in isolation from Strands types.
- **Negative / trade-off:** Claude spans two paths — newest Claude _could_ go through Mantle-Messages, but only the newest is Mantle-eligible, so we keep **all** Claude on Converse unless explicitly routed; the Messages branch exists for correctness/extensibility, not because Claude needs it. Building it now adds custom token plumbing that `OpenAIModel` gets for free.
- **Negative:** Claude-on-Mantle cannot use structured outputs (`output_config.format` → 400 on the Mantle Messages surface); Converse must be used if that feature is needed.
- **Neutral / simplification:** No IaC or schema change. `supportedModels` stays `Record<string, string>` and the user owns the configured `model_id`. Routing is an exact-string membership test against the Mantle `/v1/models` list: a Mantle-listed id (e.g. `openai.gpt-oss-20b`) routes to Mantle; a cross-region inference profile or Converse-form id (e.g. `us.anthropic.claude-…`, `…-v1:0`) is absent from that list and routes to Converse exactly as today. Mantle ids being short (`openai.gpt-oss-20b`) vs. Converse-form is therefore not a bridging problem — the two id spaces simply select different paths, which is the intended behavior.
- **Cost:** one extra `/v1/models` round-trip per session at container start (amortized, cached); respects the cold-start sensitivity recorded for agent images.
- **Positive (amendment):** the OpenAI proprietary line (GPT-5.x) is reachable via `OpenAIResponsesModel` + `bedrock_mantle_config`; strands handles both the `/openai/v1` path and per-request token minting, so the Responses branch adds no extra plumbing beyond selecting the class. Live-validated end-to-end through a real Strands `Agent` (streaming + `calculator` tool call): `openai.gpt-5.4` on Responses `/openai/v1`, and `deepseek.v3.1` / `google.gemma-3-27b-it` / `qwen3-32b` / `openai.gpt-oss-20b` on Chat Completions `/v1`.
- **Negative / trade-off (amendment):** the Responses shape differs from Chat Completions — params use `max_output_tokens` (not `max_tokens`) and reasoning is `params["reasoning"] = {"effort": …}` (not `reasoning_effort`). GPT-5.x on the Responses surface **accepts** `temperature` (unlike Claude on Mantle-Messages). The `openai.gpt-5.` prefix is a maintenance point: a future `openai.gpt-6` would need adding here and in strands' `_OPENAI_PATH_MODEL_PREFIXES`.
